In [Part 1](/articles/federating-workloads-across-clusters-placementdecision-part-1/) we covered the OCM Placement API — how to declare intent about where workloads should run using `Placement` objects, `ManagedClusterSets`, and label-based predicates. At the end of Part 1 you had a `Placement` that matched clusters by region, environment, or capacity. What you didn't have was anything acting on it.

This is where `PlacementDecision` enters the picture.

`PlacementDecision` is the output side of the scheduling loop. It is the object that the placement controller writes — a concrete, current list of clusters that satisfy your `Placement` constraints. Everything downstream — your GitOps engine, your subscription controller, your custom operator — reads `PlacementDecision` to know where to deploy. Understanding this object is what separates teams that configure multi-cluster federation from teams that operate it.

---

## What PlacementDecision actually is

A `PlacementDecision` is a namespaced Kubernetes resource, auto-generated by the placement controller in Open Cluster Management (OCM). You do not create it — you read it.

```yaml
apiVersion: cluster.open-cluster-management.io/v1beta1
kind: PlacementDecision
metadata:
  name: my-placement-decision-1
  namespace: my-namespace
  labels:
    cluster.open-cluster-management.io/placement: my-placement
status:
  decisions:
    - clusterName: prod-eu-west-1
      reason: ""
    - clusterName: prod-us-east-1
      reason: ""
    - clusterName: prod-ap-southeast-1
      reason: ""
```

Three things to internalise immediately:

**It is paginated.** A single `Placement` can generate multiple `PlacementDecision` objects, each capped at 100 cluster entries. If your placement matches 250 clusters you get three decision objects. Any consumer must enumerate all decisions with the label selector `cluster.open-cluster-management.io/placement=<placement-name>` — not just read the first object.

**It is eventually consistent.** When a cluster joins or leaves the matched set, the placement controller reconciles and updates the relevant `PlacementDecision`. Consumers should watch for changes, not read once.

**It is authoritative.** The `PlacementDecision` reflects the current view of the scheduler. If a cluster has gone offline and the placement controller has removed it from decisions, that is the signal — the cluster is no longer eligible regardless of what your Git state says.

## The scheduling loop in detail

Understanding how the placement controller produces decisions is prerequisite to trusting them.

```
ManagedCluster objects (hub)
        │
        ▼
  Placement predicates evaluated
  (label selectors, taints, tolerations,
   cluster claims, decision strategies)
        │
        ▼
  Prioritizers score eligible clusters
  (ResourceAllocatableMemory, Steady,
   Balance, custom extension points)
        │
        ▼
  PlacementDecision written/updated
  (paginated, labelled, status.decisions)
        │
        ▼
  Consumers act on decisions
  (ManifestWork, Subscription, GitOps,
   custom controllers)
```

The prioritiser step is where multi-cluster scheduling diverges from simple label matching. OCM ships three built-in prioritisers:

- **Steady** — prefer clusters that are already running the workload. Minimises churn on reconcile.
- **Balance** — spread workloads evenly across matched clusters. Good for stateless horizontal scale.
- **ResourceAllocatableMemory / ResourceAllocatableCPU** — score clusters by remaining schedulable resource. Essential for capacity-aware placement.

You compose prioritisers in a `Placement` spec:

```yaml
spec:
  prioritizerPolicy:
    mode: Exact
    configurations:
      - scoreCoordinate:
          type: BuiltIn
          builtIn: ResourceAllocatableMemory
        weight: 3
      - scoreCoordinate:
          type: BuiltIn
          builtIn: Steady
        weight: 1
```

`weight: 3` on memory means the scheduler strongly prefers clusters with available headroom but will still prefer an existing placement (`Steady`) as a tiebreaker. This combination is the right default for stateful workloads you don't want bouncing between clusters on every reconcile.

## Reading PlacementDecision in a controller

The practical challenge is that most platform code needs to enumerate decisions across all pages. The pattern using controller-runtime looks like this:

```go
import (
    clusterv1beta1 "open-cluster-management.io/api/cluster/v1beta1"
    "sigs.k8s.io/controller-runtime/pkg/client"
)

func getDecisionClusters(ctx context.Context, c client.Client, placementName, namespace string) ([]string, error) {
    decisionList := &clusterv1beta1.PlacementDecisionList{}
    err := c.List(ctx, decisionList,
        client.InNamespace(namespace),
        client.MatchingLabels{
            "cluster.open-cluster-management.io/placement": placementName,
        },
    )
    if err != nil {
        return nil, err
    }

    var clusters []string
    for _, decision := range decisionList.Items {
        for _, d := range decision.Status.Decisions {
            clusters = append(clusters, d.ClusterName)
        }
    }
    return clusters, nil
}
```

This is the correct pattern — enumerate all `PlacementDecision` objects in the namespace matching the placement label, then flatten `status.decisions` across all pages. Controllers that read only the first `PlacementDecision` object silently miss clusters beyond page one.

## Driving GitOps from PlacementDecision

The most common production pattern is using `PlacementDecision` as the scheduling input for a GitOps engine. In ACM/OCM, `Subscription` objects support this natively:

```yaml
apiVersion: apps.open-cluster-management.io/v1
kind: Subscription
metadata:
  name: nginx-subscription
  namespace: my-namespace
spec:
  channel: my-namespace/my-channel
  placement:
    placementRef:
      name: my-placement
      kind: Placement
      apiGroup: cluster.open-cluster-management.io
```

The subscription controller watches the referenced `Placement`, enumerates its `PlacementDecision` objects, and propagates the channel content (Helm chart, Kustomize overlay, raw manifests) to each decided cluster via `ManifestWork`. When a cluster drops out of the placement decision — because it became unhealthy, exceeded resource limits, or a taint was applied — the subscription controller removes the `ManifestWork` for that cluster automatically.

This is multi-cluster GitOps working correctly: placement drives scheduling, scheduling drives delivery, and delivery is continuously reconciled.

### Flux and PlacementDecision

Flux does not have native PlacementDecision integration as of Flux v2.x. The standard pattern is to use OCM's `ManifestWork` to deploy a `GitRepository` and `Kustomization` object to each decided cluster, letting each cluster's local Flux instance handle reconciliation:

```yaml
apiVersion: work.open-cluster-management.io/v1
kind: ManifestWork
metadata:
  name: flux-nginx
  namespace: prod-eu-west-1   # cluster namespace on hub
spec:
  workload:
    manifests:
      - apiVersion: source.toolkit.fluxcd.io/v1
        kind: GitRepository
        metadata:
          name: nginx
          namespace: flux-system
        spec:
          interval: 5m
          url: https://github.com/myorg/nginx-config
          ref:
            branch: main
      - apiVersion: kustomize.toolkit.fluxcd.io/v1
        kind: Kustomization
        metadata:
          name: nginx
          namespace: flux-system
        spec:
          interval: 10m
          sourceRef:
            kind: GitRepository
            name: nginx
          path: ./clusters/prod
          prune: true
```

A controller watches `PlacementDecision`, and for each decided cluster creates a `ManifestWork` in that cluster's namespace on the hub. Each cluster's Flux instance then runs independently, pulling from Git and reconciling locally. This pattern gives you the best of both worlds: OCM handles cross-cluster scheduling decisions, Flux handles per-cluster reconciliation.

## Decision strategies: Topology spreading

A common requirement is ensuring workload replicas span failure domains — regions, availability zones, or cloud providers. OCM's `spreadConstraints` in the `Placement` spec controls this:

```yaml
spec:
  numberOfClusters: 6
  spreadConstraintsOnClusters:
    - topologyKey: region
      topologyKeyValues:
        - eu-west-1
        - us-east-1
        - ap-southeast-1
      maxSkew: 1
      whenUnsatisfiable: DoNotSchedule
```

`maxSkew: 1` means no region can hold more than one extra cluster's worth of the workload compared to the least-loaded region. `whenUnsatisfiable: DoNotSchedule` means if the constraint cannot be met — say only two regions have healthy clusters — the scheduler will not schedule at all rather than violate the spread requirement.

This mirrors the `topologySpreadConstraints` concept in pod scheduling but operates at the cluster level. It is the right control for teams with regulatory requirements around data residency or DR mandates requiring active-active deployment across geographic regions.

## Handling cluster churn

In production multi-cluster environments, clusters disappear. Node groups scale to zero, cloud regions have outages, maintenance windows take clusters offline. Your placement-driven workloads need to handle this gracefully.

The key behaviours to verify in your setup:

**Scheduled removal.** Apply a `ManagedClusterTaint` before a planned maintenance window. The placement controller removes the cluster from active `PlacementDecision` objects, your subscription/ManifestWork controller deprovisions from that cluster, and when the taint is removed post-maintenance the cluster re-enters the decision set.

```yaml
apiVersion: cluster.open-cluster-management.io/v1
kind: ManagedCluster
metadata:
  name: prod-eu-west-1
spec:
  taints:
    - key: cluster.open-cluster-management.io/unavailable
      effect: NoSelect
      timeAdded: "2026-08-28T02:00:00Z"
```

**Unscheduled removal.** When a cluster's hub connection drops, the `ManagedCluster` status reflects `ManagedClusterConditionAvailable=False`. A `Placement` with a `clusterConditionsTolerations` policy can decide whether to keep scheduling to that cluster or remove it from decisions. The conservative default is to remove it.

**Rebalancing.** When a previously removed cluster returns, the Steady prioritiser resists immediately moving workloads back. This is the correct behaviour — you want explicit human sign-off before reintroducing a cluster that had an incident, not automatic rebalancing that might mask a recurring problem.

## What to monitor

For any team operating placement-driven federation in production, three signals matter most:

| Signal | What it means |
|---|---|
| `PlacementDecision` count delta | Clusters entering/leaving the decided set — track this as a metric, alert on unexpected churn |
| `ManifestWork` applied vs available | Work created by the hub vs successfully applied on the cluster — gaps indicate delivery failures |
| Placement score distribution | How prioritiser scores are distributing across clusters — sudden convergence on one cluster suggests a capacity imbalance |

The OCM hub exposes these via its controller metrics. Feeding them into your Prometheus stack gives you a scheduling observability layer that most multi-cluster deployments currently lack.

## Where Part 3 will go

`PlacementDecision` gives you cluster-level scheduling. What it does not give you is workload-level scheduling within a cluster — pod topology, affinity, resource quotas per workload type. Part 3 will cover how placement-driven federation composes with in-cluster scheduling controls, and where the handoff between OCM and the Kubernetes scheduler should sit in a mature platform.
